# AH Snapshot 設計備忘

## 資料流

```
遊戲內（AHSnapshot 插件）                       電腦上（AHSync 系統匣程式）              雲端共用資料夾
Auctionator 全掃 → AHSnapshotDB.realms[鍵].scans
登出 → AHSnapshotOutbox（自己最近 14 天）  ──上傳──→  <自己名字>.txt
登入 ← AHSnapshotInbox（匯入後清空）       ←─合併──  其他人的 <名字>.txt
       → AHSnapshotDB.shared[來源][鍵].scans
```

- 拍賣場鍵跟 Auctionator 一致（`Auctionator.Variables.GetConnectedRealmRoot()`，Forever 實測是 `PvE`）。
- 掃描時間用 `GetServerTime()`，不同人的時間才對得起來。
- 同步程式只在遊戲**關著**時寫存檔（遊戲登出會覆蓋存檔）；寫之前備份到 `%APPDATA%\AHSnapshotSync\backups`（留 5 份）。
- 每個人只寫自己的雲端檔案，不會互相覆蓋；朋友的資料只在本機合併，不會再轉傳（不會繞圈）。

## 交換格式（版本 1）

紀錄用 `~` 分隔（雲端檔案裡換成一行一筆），欄位用 `^` 分隔。`% ^ ~ " \` 與控制字元寫成 `%XX`，
所以字串放進 WoW 存檔不需要任何跳脫，外部工具找雙引號就能切出來。

| 類型 | 欄位 | 說明 |
|---|---|---|
| `V` | 格式版本、來源名字、匯出時間 | 每段資料的開頭；來源名字由同步程式依檔名填入 |
| `I` | 物品鍵、名稱、品質、收購價、分類、子分類、堆疊 | 物品資料（本機已有名稱就不覆蓋） |
| `S` | 拍賣場鍵、t、gap、diff、tl、n、zone、列格式版本、推估版本 | 一次掃描，後面接它的 `R`；推估版本 < 2（或沒有這欄）的只收價格與架上量，推估歸零、diff=0 |
| `R` | 物品鍵、逗號分隔數字 | 欄位依 `S.ROW_FIELDS`（只往後加，缺的當 0） |
| `D` | （保留）| 每日彙整，見下 |

不認得的類型直接略過，舊版插件讀新資料不會壞。改格式要升 `V` 的版本號；列欄位改變要升 `S` 最後一欄（`S.ROW_SCHEMA`）。

## 賣出推估（推估版本 2：依單價分層）

Forever 的全掃（`C_AuctionHouse` replicate）**沒有賣家名字、也沒有拍賣編號**，剩餘時間是 1～4 級
（1＝30 分內、2＝30 分～2 小時、3＝2 小時以上、4＝很長，保守當成 8 小時以上）。所以不比對「哪一筆」，
而是比對每個物品「每個直購單價有多少數量」（一層＝同一單價的所有上架，另記各剩餘時間分級的數量）。

快照 `ah.prev[物品鍵] = "2|s|單價:數量:分級1,分級2,分級3,分級4;..."`（`s` 可堆疊、`u` 不可堆疊），
`ah.prevVersion = 2`。不是這個格式（1.1 版逐筆指紋）就當第一次掃描，不比對。

每層數量的變化：減少＝候選賣出，增加＝新上架。然後：

- **可堆疊商品**（`items[鍵].stack > 1`；不知道時看有沒有一次多個的上架）：買家一定從最便宜的買起。
  從最低價往上走，連續被吃掉的層才算賣出；遇到沒動的層或只被吃掉一部分的層，之後更貴的層的減少都算**撤單/重上**。
  - 被吃掉的底層，若同樣數量（差 5% 內）出現在更便宜的價位 → 壓價重上，不算賣出。
  - 數量不同時，更便宜價位的新上架先抵掉減少量（寧可少算賣出）。
  - 撤單的數量若和別的價位新增的數量相近 → 換價重上，那筆新增不再算新上架。
  - 部分購買只算真正少掉的數量（200 → 180 只算 20）。
- **不可堆疊商品**（裝備等，每件 1 個）：逐件比對，買家可以挑任何一件，所以任何減少都是候選賣出。
  **沒有賣家名字，撤單沒重上也會被算成賣出**（已知會偏高）。
- **剩餘時間**：每層減少的數量，先算到「間隔內可能已到期」的分級（剩餘時間下限 ≤ 間隔），剩下的才算賣出。
- **只能競標**（直購價 0）：減少一律算到期。
- **成交筆數 soldN**：可堆疊＝被吃掉的價位層數（一整疊被買走或一層被吃掉都只算 1 次）；不可堆疊＝件數。
- **成交金額**：賣出數量 × 該層單價。

### 已知限制

- 最便宜那一層裡的撤單，和被買走分不出來，會算成賣出（底下更便宜的都被買光時，下一層的撤單也一樣）。
- 裝備類撤單會被算成賣出（沒有賣家名字）。
- 30 分內就要到期的上架消失時，一律保守算成可能到期 → 稍微低估。
- 兩次掃描之間新上架又被買走的，看不到 → 低估。
- 間隔超過 8 小時的比對不算（大部分上架都可能已到期）。

用真實存檔的快照做模擬（`tests/check_realdata.py`，2218 種物品、13999 筆）：可堆疊商品正確答案賣出 4552，
推估 4585（+0.7%）；裝備正確答案 312，推估 366（+17%，來自撤單）。舊的逐筆指紋演算法同情境估約 10049。

### 舊資料（資料版本 3 升級）

1.0／1.1 版用逐筆指紋，還誤把剩餘時間 +1（最長那級變成 5、被當成可能到期），推估不可信。
插件升級時（`S.MigrateToV3`，只做一次）：所有掃描保留量與價格（列的前 5 欄），推估欄位歸零、`diff=0`；
舊快照丟掉，下一次全掃當第一次。朋友資料中推估版本 < 2 的也一樣處理；匯出、匯入時同樣過濾。

## 估算與可信度

- 推估欄位都標「(估)」，數字前加「約」。
- **換算每日：分母至少 1 天**。觀察 3 小時看到 1 筆成交，每日賣出就是 1，不會放大成 8。
  賣出量本來就不會超過觀察期間從架上消失的量，所以每日數字不會超過實際看得到的供給。
- **低可信度**：成交筆數 < 3，或有效觀察 < 12 小時。顯示灰色加「?」，依推估欄位排序時一律排在可信的後面
  （不論升降冪）。成交均價只來自 1～2 筆成交時也標灰色。
- 常數在 `Core.lua`：`S.MIN_DAY_SECONDS`、`S.CONF_MIN_SALES`、`S.CONF_MIN_HOURS`。

## 合併分析的規則

- 架上量、最低價、中位價：所有來源中**最新**那次掃描。
- 賣出量：每次比對代表區間 `[t-gap, t]`。所有來源的區間放一起，重疊的只取一個（優先間隔短的，`S.PickIntervals`），
  只累加被選中的區間，觀察時間也只算被選中的。間隔超過 8 小時不算。
- 只有自己一個來源時，連續掃描本來就不重疊，結果和以前一樣。

## 之後加「歷史彙整」怎麼接

已經有：`S.RollupDaily(來源, 時區秒數)` 把掃描彙整成「每天每物品一列」（最低價、中位價平均、最大架上量、賣出、
成交金額、可能到期、觀察秒數），用同一套不重疊規則，有測試，**還沒自動啟用**。

接上的步驟：

1. **遊戲內**：`AHSnapshotDB.realms[鍵].daily[天編號] = { observed, scans, items = { [物品鍵] = "min,medAvg,maxQty,sold,soldValue,soldValueQty,expired,n" } }`，
   掃描超過 N 天（例如 14 天）時先彙整進 `daily` 再刪掉逐次掃描。`shared[來源][鍵].daily` 同樣結構。
   需要一個「已彙整到哪天」的標記，避免重複彙整。
2. **交換格式**：加 `D^拍賣場鍵^天編號^observed^scans^每日列格式版本`，後面接 `R` 列（內容是每日列）。
   舊版插件遇到 `D` 會略過、後面的 `R` 也因為沒有目前掃描而被丟掉，不會誤當成掃描。
3. **雲端**：每個人的 `<名字>.txt` 只放近期逐次掃描；較舊的每日彙整放 `archive/<名字>.txt`（同步程式目前會忽略子資料夾，
   之後再加讀取）。也可以由任何一個人的同步程式產生 `archive/_合併.txt`（底線開頭的檔案目前也會被忽略）。
4. **分析**：`S.Analyze` 讀「近期逐次掃描」＋「更早的每日紀錄」：每日紀錄只拿 sold/soldValue/expired/observed 加總，
   和逐次掃描的時間範圍以「最早一筆逐次掃描的那天」切開，不重疊。視窗的 30 天、更長天數就靠每日紀錄。

資料版本：`AHSnapshotDB.version`（目前 3）、交換格式 `V` 版本（目前 1）、列格式 `S.ROW_SCHEMA`（1）、
推估版本 `S.EST_VERSION`（2）、快照格式 `S.PREV_VERSION`（2）、每日格式 `S.DAILY_SCHEMA`（1）。
